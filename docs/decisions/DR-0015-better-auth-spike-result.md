# DR-0015: Better Auth spike result (DR-0011): it fits inside the structure; whether to adopt it is the owner's call

- Status: proposed (owner decision and signature pending; the builder cannot accept its own record)
- Date: 2026-11-02
- Rules: AUTH-1, AUTH-2, AUTH-3, AUTH-4, ROUTE-1, ROUTE-2, TENANT-1, TENANT-3

## Context
DR-0011 asked whether Better Auth (`better-auth` 1.7.15, pinned) can sit behind Bulkhead's `authenticate` hook without weakening it, and set a pass/fail bar (a) to (g). This record is the spike's result. Nothing shipped changed: the default demo and `@kalahroudi/bulkhead-auth` are untouched except that `createDemoApp` now takes an optional auth kit. The spike is `packages/auth-betterauth` (private, unpublished) run by `examples/demo-betterauth`, and `gate:phase4` now runs the same probes against it.

### What the spike is
- A custom Better Auth database adapter whose only way to storage is a `TenantDb`, built per request (`src/adapter.ts`). One Better Auth instance is built per request around that handle; the spike's own code keeps no cross-request state. The library itself keeps a global holder for its async-context instances and a module-level in-memory rate-limit map; the second is never reached because its router is not mounted.
- Sign-up, sign-in, session lookup and sign-out go through Better Auth. The HTTP contract is the shipped one (same paths, statuses, bodies), registered route by route with policies, so the AUTH probes run unmodified. Better Auth's own catch-all handler is not mounted.
- The password hash is overridden to the shipped PBKDF2. API keys, the login throttle and bootstrap stay ours.

### Result against the bar
- (a) Met on the local target: every TENANT, AUTH and CRYPTO probe passes against it (`verify-kernel.ts --app examples/demo-betterauth`). One probe, `role-change-revokes`, was extended during the spike (see (d)) and now runs for both demos; the others are unchanged. The catalog entries with `app: "examples/demo-betterauth"` prove those probes can fail against the spike's code: each is killed by named probes, or is a named gap killed by the spike's unit tests (44 entries: 25 killed by probes and 19 gaps killed by unit tests).
- (b) Met: all state goes through `TenantDb`; the schema lives in the tenant's Durable Object (`src/schema.ts`). Better Auth's in-memory rate limit and telemetry are not used (telemetry disabled).
- (c) Met for what was built: every route is registered individually with a policy and appears in `examples/demo-betterauth/route-manifest.json`. Only email and password sign-in is served. Password reset, MFA, passkeys and OAuth, the reasons to adopt Better Auth, were not built or evaluated, and each would need its own route, policy, probe and mutation entries.
- (d) Met: `cookieCache` is off and the session and user are read from the database on every request. The attacker found that a probe sending only the token cookie could not see a cache that defers revocation, and extended `role-change-revokes` to replay the whole cookie jar. Other probes still send only the token cookie.
- (e) Met, with a change: Better Auth names the cookie `__Secure-<name>` when told to use secure cookies, giving an invalid `__Secure-__Host-bk_session`. The spike sets `useSecureCookies: false` and names the cookie `__Host-bk_session` in full; the library then forces `Secure`, and a unit test checks the attributes. Better Auth's own origin check does not run when its API is called directly (a sign-in with `Origin: https://evil.example` returned 200; a unit test records this and fails if the library changes), so the shipped same-origin rule in the hook is what enforces CSRF, as before.
- (f) Not verified. Local workerd does not enforce CPU limits. Measured on Node with `packages/auth-betterauth/scripts/measure.ts`: Better Auth's default scrypt hash took about 49 ms against about 8 ms for PBKDF2 at 100,000 iterations, so the override is needed on any plan with a low CPU limit. Building an instance and reading a session cost about 0.4 ms. These are Node timings, not Workers CPU time.
- (g) Not evaluated: API keys stay ours, with about 30 lines duplicated from the shipped authenticate path. Better Auth's key plugin was not read.

### Costs and differences found
- Bundle (from `wrangler deploy --dry-run`, reproduced by the same script): the Worker went from 111 KiB (29 KiB gzip) to about 2,035 KiB (360 KiB gzip). `nodejs_compat` is required.
- Dependencies: 21 packages added to the lockfile, including `kysely`, `zod`, `jose`, `better-call` and `@noble/*`, plus adapters for ORMs we do not use.
- Session tokens are stored in plaintext in `session.token` (the shipped auth stores only a SHA-256). The cookie value carries an HMAC signature under a Worker secret, so a database read alone is not enough to forge a cookie, but this is weaker than the shipped design and the secret is a new boot-time requirement (the spike fails closed without it but has no boot check like BOOT-1).
- No idle timeout. The shipped auth ends a session after 24 hours idle. Better Auth's server-side expiry slides, but the hook discards the refreshed cookie it would send, so the client's cookie keeps its original 7-day lifetime; that is more conservative, not less.
- Bootstrap is weaker: Better Auth creates a user in several statements, so "only while empty" is a pre-check, a create of a disabled owner, and one guarded update that enables it only while it is the only user. A loser is deleted before it could ever sign in. Two racing claims may both lose (both get a 409) or one may win; the tests require at most one user and agreement between the response and the database, not a particular winner.
- There is no multi-statement transaction through `TenantDb`, and Better Auth's sign-up does not roll back: with the account insert failing, the first version of the spike left an owner row with no account, and every later bootstrap answered "tenant already has users". The review found this. The routes now remove a partial user and report a storage fault as a 500, never as a conflict (unit-tested). Cleanup after a failure deletes by email, so a concurrent sign-up of the same email that fails in the same instant could be cleaned up too.
- Better Auth's `signOut` logs a failed session delete and still answers success; the first version of the spike returned 200 with the session alive. The route now deletes by token itself and fails with a 500 if the row remains (unit-tested).
- The adapter initially chained AND and OR clauses in order, which SQL precedence turns into a different query from the one Better Auth's own adapters build; it now builds (every AND) AND (any OR). Email and password never uses OR in 1.7.15, so this was latent, but plugins would reach it. Writes with an empty condition are refused.
- Calling `auth.api` skips whatever lives in Better Auth's handler layer (its rate limit, and the origin check above). Anything we want from there, we rebuild.
- Dates are stored as ISO text. A comparison written against numbers silently never matches; one such bug was found and fixed during the spike.

## Decision
1. **Outcome under DR-0011 item 4: the substrate passes, the features are unproven.** Sessions, cookies and sign-in run inside the structure and the probes cannot tell the difference. That was not the reason to evaluate it. The spike did not build password reset, MFA, passkeys or OAuth, so it does not show that the feature layer fits. Check: `gate:phase4`. No check: the judgement that the features are unproven is a statement about what was not built.
2. **Recommendation, not a decision: do not retire our session and key core on this evidence.** Adopting Better Auth for sessions alone buys nothing we lack and costs the bundle size, 21 dependencies, plaintext tokens at rest and a lost idle timeout. A second time-boxed spike should build password reset and TOTP MFA on this kit, with probes and mutation entries, and only then should the owner decide. If the owner prefers to stop here, the spike stays unwired and can be deleted. No check: this is advice to the owner.
3. **Nothing from the spike is wired into the default demo or shipped.** `packages/auth-betterauth` is private and unpublished and `examples/demo-betterauth` is separate. The default demo runs the same auth, routes and probes as before; the changes that touch it are the optional `AuthKit` parameter of `createDemoApp` (unused by default), the `--app` option of the launcher and mutation runner, and the extended `role-change-revokes` probe. `gate:phase4` now also runs the probes against the spike. Check: `script:scripts/verify-kernel.ts`, `gate:phase4`.
4. **Discipline kept.** The spike's lines have mutation entries killed by probes or named gaps killed by unit tests, and the verifier gained one fix found by attacking the spike. Check: `test:packages/verify/test/mutations.test.ts::DR-0007 item 4`, `mutation:ba-cookie-cache-defers-revocation`, `mutation:ba-login-lockout-removed`, `test:packages/auth-betterauth/test/gaps.test.ts::ba-login-lockout-removed`.

## Consequences
CLAUDE.md "Current state" records the spike as done and awaiting the owner's decision. The next item in the agreed order, making the verifier usable against an app other than the demo, is partly started: the kernel launcher and the mutation runner take `--app`. A green report still means no known leak paths, not proof that none exist; the CRYPTO and AUTH rules stay `proposed`.

Known limits: (f) is unverified on real Workers; the spike was exercised on email and password only; probes other than `role-change-revokes` still send only the token cookie, so a cookie-cache bypass on logout is not covered; the probes look for the cookie by its `__Host-` name, so dropping the prefix shows up as a broad failure rather than a precise `cookie-flags` one; the adapter's `limit` default (100 when none is given), `offset`, case-insensitive `in`, and the `changes` count (Durable Object rows written, not rows affected) have no unit coverage; the library's other endpoints and its rate limit are not served or used; a missing signing secret fails closed but has no boot check, and then a login for an existing email is a 500 where an unknown email is a 401.
