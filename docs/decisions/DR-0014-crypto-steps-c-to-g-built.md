# DR-0014: DR-0010 steps (c) to (g) built: classification enforcement, sealed handle, key hierarchy, nonce counter, write-only secrets

- Status: proposed (owner acceptance and signature pending; the builder cannot accept its own record)
- Date: 2026-11-02
- Rules: CRYPTO-1, CRYPTO-2, CRYPTO-3, CRYPTO-4, CRYPTO-5, BOOT-1

## Context
DR-0010 (accepted by the owner) fixed the design; step (a) built the inspector and probes, step (b) the crypto port. This record states what steps (c) to (g) built and where the build departs from or narrows DR-0010. The core and demo were written by the builder; the probes, seeded bugs and mutation entries (`packages/verify/`) by a separate attacker session; the BOOT-1 check is a launcher script.

### What was built
- `packages/core/src/crypto/`: `classification.ts` (parse, `sealedCheck`, `enforceClassification`), `keys.ts` (master keys, key ring, sealer), `nonce.ts`, `ring.ts`. `TenantDb` gained `seal` and `open`; `RouteContext` gained `keys.rotate()` and `keys.shred()`; `createApp` takes `classification`.
- The demo classifies every column (`examples/demo-app/bulkhead.classification.json`), seals `notes.text`, and has a write-only `tenant_secrets` table with `POST /secrets` (owner) and a metadata-only `GET /secrets`, plus owner routes `POST /admin/rotate-key` and `POST /admin/shred`.

## Decision
1. **Classification is enforced where the data lives.** When a tenant's database initialises, every column of every app table must be classified, every classified column must exist, and every `sensitive` or `secret` column must carry the sealed-value CHECK, or the tenant refuses to initialise. Runtime tables are exempt by exact name only (`_bulkhead_meta`, `sqlite_*`, `_cf_<UPPERCASE>`, `__miniflare_do_name`). The same protection holds after initialisation: in an app with a classification a route may run only a single `select`, `insert`, `update`, `delete`, `replace` or `with` statement, so it cannot add a table or column, change a CHECK, or run `pragma ignore_check_constraints` (a reviewer showed all three bypass the CHECK). The CHECK must be real SQL: a comment, or a default value that spells it, does not count. Check: `test:packages/core/test/sealing.test.ts::CRYPTO-1: with classified data a route can run only single data statements: no pragma, no DDL, no second statement`, `test:packages/core/test/sealing.test.ts::CRYPTO-1: the sealed-value CHECK must be real SQL: a comment or a default value that spells it does not count`, `test:packages/core/test/sealing.test.ts::CRYPTO-1: runtime-table exemptions are exact names, so an app table cannot hide behind a prefix`, `test:packages/core/test/sealing.test.ts::CRYPTO-1: an unclassified column, a missing CHECK or a stale classification stops the tenant initialising`, `probe:storage-canary-at-rest`.
2. **The CHECK is stricter than DR-0010 wrote, but only approximately the envelope shape.** It requires `bk1:`, a non-zero first version character, a 16-character nonce position and a non-empty remainder, case-sensitively and with base64url characters only, instead of `LIKE 'bk1:%'`. SQLite's `GLOB` cannot count repetitions, so values such as `bk1:1abc:AAAAAAAAAAAAAAAA:x` pass. A forged but well-formed value still passes: shape is not authenticity, so the sealed write path and the verify canary remain the backstop, as DR-0010 item 6 already said. Check: `test:packages/core/test/sealing.test.ts::CRYPTO-1: the database itself rejects plaintext, a look-alike prefix and wrong-case envelopes in sealed columns`.
3. **Nonces are a per-(tenant, key version) counter in the tenant's own database,** reserved by one statement and one read with no await between, so two reservations never return the same number. This differs from DR-0010 item 3 in one way: the number is reserved before the write rather than in the same operation, so a failed write burns a number. Gaps are harmless. Within one live tenant database, reuse cannot happen because the object runs one request's storage step at a time; the unit test shows uniqueness and per-version counting, not concurrency, which the runtime provides. Check: `test:packages/core/test/sealing.test.ts::CRYPTO-4: nonce reservations are unique and counted per key version`, `probe:nonce-uniqueness-and-rotation`.
4. **Key hierarchy as DR-0010 item 5, with one addition.** A versioned master key wraps each tenant's data key in the control-plane D1, with tenant, version and master version as wrap AAD. A shredded tenant keeps emptied rows, so it is never re-keyed, and a key insert is refused while any of the tenant's rows is shredded, so a rotation racing a shred cannot leave a live key. A tenant is keyed at provisioning, not on first write. Shredding is effective in the shredding isolate at once and in others within the 60-second cache. Rotation adds a version and old versions stay readable. Check: `test:packages/core/test/sealing.test.ts::CRYPTO-3: a rotation that races a shred cannot leave a live key behind`, `test:packages/core/test/sealing.test.ts::CRYPTO-3: shredding makes the tenant's data unreadable, and a shredded tenant is never re-keyed`, `test:packages/core/test/sealing.test.ts::CRYPTO-3: the data key cache lasts 60 seconds, so a shred in another isolate bites within a minute`, `test:packages/core/test/sealing.test.ts::CRYPTO-3: shredding a tenant that was never keyed still leaves marker rows, so it is never keyed afterwards`, `test:packages/core/test/sealing.test.ts::CRYPTO-4: rotation adds a version, old values still open, new values use the new key`, `probe:shredding-makes-data-unreadable`.
5. **AAD binds tenant, table, field and key version only (owner answer 2 to DR-0010).** A sealed value opens only in its own tenant, table and field, and the sealer never opens a field outside the encrypted classes. Check: `test:packages/core/test/sealing.test.ts::CRYPTO-2: a sealed value opens in its own tenant, table and field, and nowhere else`, `test:packages/core/test/sealing.test.ts::CRYPTO-2: the tenant is part of the AAD at the sealer level, even when two tenants share one key`, `probe:aad-transplant-fails`.
6. **Secrets are write-only by structure.** The handle refuses to open a `writeOnly` field, so a route cannot return one even by mistake; the demo has a store route and a metadata listing and no read route. Check: `test:packages/core/test/sealing.test.ts::CRYPTO-5: a write-only field can be sealed but the handle never opens it; unsealed fields cannot be sealed`, `probe:secret-write-only-readback`. Limit: server-side use of a stored secret (an outbound call, say) has no path in v1.
7. **BOOT-1 is checked by the launcher, not by verify.** `scripts/verify-boot.ts` boots the demo with each key missing or malformed and requires every route to answer 500 "service misconfigured" and no tenant or control-plane database to be written, with a control run that must serve and must write. Keys are required whenever the app declares a classification. Check: `script:scripts/verify-boot.ts`, `gate:phase4`.
8. **A tenant whose data keys were destroyed answers 410;** every other key fault (a missing master-key version, a corrupt wrapped key, an envelope naming an unknown key version) is an ordinary 500, so an operator can tell destroyed data from a fault. Check: `probe:shredding-makes-data-unreadable`, `test:packages/core/test/sealing.test.ts::only a destroyed tenant key answers 410; a forged key version or a missing master key is an ordinary 500`.
9. **Honest limits.** Everything in DR-0010 item 9 stands (master key is a Worker secret, no HSM, 60-second key cache in memory, backups not reached). Also: the AAD does not bind the row, so a swap between rows of one column opens (the transplant probe's control shows it); wrapped keys in the control-plane D1 were not transplanted; the 60-second window in other isolates is not exercised by any probe; a nonce counter that is rolled back while its key survives (restoring a tenant's Durable Object from an earlier point while its control-plane key row remains) would reuse nonces under that key, and nothing ties a counter to its key; restore must re-key the tenant first, and that procedure is not built; wrapping a data key under the master key uses a random nonce, which is within bounds for the few wraps a master key ever does but is not a counter; CRYPTO-1 and CRYPTO-3 are verified only on a local target with the persisted directory (elsewhere they report unverified); BOOT-1 covers the cases the script lists and sends four requests per case, not every route and not every misconfiguration; the script refuses to run if `examples/demo-app/.dev.vars` exists. The CRYPTO rules stay `proposed`; no attestation exists until Phase 7. No check: these are limits, not behaviours.

## Consequences
`gate:phase4` now runs the CRYPTO and BOOT-1 checks. `pnpm dev` for the demo needs master keys (`.dev.vars.example`). Auth hashes stay hashed, not sealed, and are classified `internal`. A green report means no known leak paths, not proof of none.
