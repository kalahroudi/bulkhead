# DR-0011: Evaluate Better Auth behind the existing authenticate hook (time-boxed spike)

- Status: proposed (owner agreed to the approach in session on 2026-10-13; the spike has not started and nothing here changes the shipped auth)
- Date: 2026-10-13
- Rules: AUTH-1, AUTH-2, AUTH-3, AUTH-4, ROUTE-1, ROUTE-2, TENANT-3

## Context
`@kalahroudi/bulkhead-auth` is about 400 lines of glue over WebCrypto (DR-0006). What it does not have is the commodity feature layer: password reset, email verification, MFA and passkeys, OAuth/SSO, session listing, audit. Those are the features that are most dangerous to hand-build. Better Auth is a TypeScript auth library that provides them. The question is whether it can sit inside Bulkhead's structure without weakening it. The probes for AUTH-1..4 are black-box and implementation-independent, so the question is testable.

What the vendor's documentation says (read 2026-10-13; anything not stated there is marked unverified):
- **Database:** built-in Kysely (SQLite/D1, Postgres, MySQL, MSSQL), Drizzle and Prisma adapters; custom adapters are implied but their API was not on the pages read. A database per request (multi-tenant) is not covered. Durable Objects are not mentioned. A `SecondaryStorage` key-value interface (`get`, `getAndDelete`, `increment`, `set`, `delete`) exists for sessions, verification records and rate limits. ([database docs](https://www.better-auth.com/docs/concepts/database))
- **Mounting:** a single catch-all handler, `app.all("/api/auth/*", ...)`, taking the raw Request, and it needs `nodejs_compat` (it uses `AsyncLocalStorage`). How per-request env and bindings reach it was not documented. ([Hono integration](https://www.better-auth.com/docs/integrations/hono))
- **Sessions:** a `session_token` cookie plus a session table; with `cookieCache` on, revoked sessions can stay valid on other devices until the cache expires, and role or user changes may not apply immediately; `disableCookieCache` forces a database read. The `__Host-` prefix, `Secure` flag and CSRF/origin behaviour were not covered by the pages read. ([session management](https://www.better-auth.com/docs/concepts/session-management))
- **Password hashing:** scrypt by default, reportedly customisable. Third-party sources only, so unverified, and the Workers CPU interaction is unverified. ([search results](https://news.hada.io/topic?id=27399))

## Decision
1. **Run a time-boxed spike, behind the existing hook, in a new unfrozen package** (`packages/auth-betterauth`, not wired into the demo by default) so shipped auth is untouched while it runs. The spike builds the smallest thing that can answer the pass/fail questions below, no more. Check: `gate:phase4`. No check: the spike's own result is the evidence; this choice only bounds the work.
2. **Pass/fail bar, all required for any adoption of the session and key core:** (a) every AUTH-1..4 probe passes unmodified against it, run through `scripts/verify-kernel.ts`; (b) all of its state is read and written through `TenantDb`, with nothing in the control plane or a global; (c) every route it serves has a manifest entry with a policy, so the catch-all is split into individually registered routes (ROUTE-1/2); (d) a role change, disable or logout takes effect on the next request, with `cookieCache` off or proven not to defer revocation; (e) cookies keep `__Host-`, `Secure`, `HttpOnly`, `SameSite=Lax` and the same-origin write check, or an equivalent proven by `cookie-flags` and `csrf-origin`; (f) it runs inside the Workers CPU limit on the unmodified gate; (g) API-key role capping and permission scoping match DR-0006 item 4, or the keys stay ours. Check: `probe:cookie-flags`, `probe:csrf-origin`, `probe:logout-revokes`, `probe:role-change-revokes`, `probe:api-key-scope`, `probe:key-revocation`, `probe:authority-matrix`.
3. **Mutation catalog entries ship with the spike,** per the project discipline: each security-relevant line the adapter adds gets a mutation entry that a probe must kill, or a named gap that unit tests must kill. Check: `test:packages/verify/test/mutations.test.ts::DR-0007 item 4`, `gate:phase4`.
4. **Outcomes, decided up front.** Pass (a)..(g): adopt it for sessions and keys and retire our core, in its own PR with a decision record. Pass only for a feature subset (for example reset, MFA, OAuth, and not sessions or keys): adopt it for those features only, and keep our session and key core, because two session systems in one app would be worse than either. Fail the bar in a way that cannot be fixed with a thin adapter: do not adopt it, record why, and put the missing features on a short list built on audited primitives. In every outcome, reset, MFA and SSO are not hand-built. No check: this is a decision rule for the owner and the builder, applied to the spike's result.
5. **Unverified items to settle first,** each a spike task: the custom-adapter interface and whether it can target a per-request Durable Object handle; how per-request bindings reach the handler; the exact password-hash override and its CPU cost on Workers; the cookie name and prefix it sets; its origin/CSRF behaviour; its API-key plugin semantics. No check: these are research tasks whose answers go into the spike result, not behaviours.
6. **Dependency risk is part of the evaluation.** A third-party dependency becomes part of the security core: pin versions, review the lockfile diff, and treat its release cadence and advisories as a standing cost. The spike records the dependency count and size it adds. No check: supply-chain posture is not enforced by any current check, and a lockfile-diff or audit step is owed if it is adopted.

## Consequences
Until the spike reports, shipped auth, its probes and its catalog entries are unchanged. The spike is scheduled after the in-flight probe PR merges, and DR-0010's crypto work is independent of it, except that sealed fields and auth tables share `TenantDb`. CRYPTO and AUTH rules stay `proposed`. A green report still means no known leak paths, not proof of none.
